# v1.2 — File Attachments on Tasks (Design)

**Date:** 2026-06-11
**Status:** Approved (brainstorming) — pending implementation plan
**Spec addendum target:** §13.5 (flips the v1 "file attachments" non-goal)
**Branch:** `feature/file-attachments` (from `develop`)

## Summary

Add file attachments to tasks. Files are stored in MinIO (S3-compatible) via the
Tasks service. Uploads/downloads are **proxied** through the Tasks service so MinIO
stays private. Per-file cap of 10 MB with a common-types whitelist. Attach/remove
events integrate fully with the v1.1 features: they broadcast live over the existing
board SignalR hub and emit integration events that surface in the per-board activity
feed.

## Decisions (locked during brainstorming)

| Decision | Choice | Rationale |
|---|---|---|
| Storage backend | MinIO (S3-compatible) | Fits "one `docker compose up`"; maps cleanly to free-tier S3/R2/B2 in prod. |
| Owning service | Tasks (sub-resource of `TaskItem`) | Authorization mirrors existing task mutations; a dedicated Files service would be over-engineering. |
| Upload/download flow | Proxied through Tasks | Single auth path (existing JWT), MinIO stays private, simplest local/prod URL story. |
| Size cap | 10 MB / file | Sensible for a task manager. |
| Type policy | Whitelist | Images (png/jpg/gif/webp), PDF, plain text, common office docs, zip. Validate content-type **and** extension; magic-byte sniff for declared image/PDF. |
| v1.1 integration | Both | Live SignalR broadcast + activity-feed event. |
| Delete authorization | Any board member | Collaborative; mirrors task mutations. |
| Max attachments / task | 20 | Guardrail against abuse. |

## Architecture

Attachments follow the **`ChecklistItem` pattern** (spec §13.2): an independent child
collection of `TaskItem` whose mutations are last-write-wins and **deliberately do NOT
advance the parent task's `RowVersion`**. Two members attaching files at the same time
must never produce a 409.

### Domain (Tasks)

New entity `Attachment` — private setters + factory, no public setters.

| Field | Type | Notes |
|---|---|---|
| `Id` | `Guid` | |
| `TaskItemId` | `Guid` | FK to parent task |
| `FileName` | `string` | Original client filename — **display metadata only** |
| `ContentType` | `string` | Validated MIME type |
| `SizeBytes` | `long` | |
| `StorageKey` | `string` | Server-generated S3 object key; client filename never trusted here |
| `UploadedById` | `Guid` | |
| `UploadedAt` | `DateTimeOffset` | All timestamps `DateTimeOffset`, per project rule |

`StorageKey` format: `boards/{boardId}/tasks/{taskId}/{guid}`. The original filename is
stored only as the `FileName` metadata column; it is sanitized and returned for display
and `Content-Disposition`, never used to build the storage key.

### Application

- **`IFileStorage` port** (Application layer — keeps the onion dependency rule intact):
  - `Task PutAsync(string key, Stream content, string contentType, CancellationToken ct)`
  - `Task<Stream> OpenReadAsync(string key, CancellationToken ct)`
  - `Task DeleteAsync(string key, CancellationToken ct)`
- Commands: `UploadAttachmentCommand`, `DeleteAttachmentCommand`. Handlers return
  `Result<T>` (FluentResults) — expected failures (not found, not a member, too large,
  bad type, over the 20-attachment cap) are `Result.Fail(...)`, never thrown.
- `AttachmentDto` embedded in the existing `TaskDto` on read.
- Validation enforces the 10 MB cap and type whitelist (content-type **and** extension;
  magic-byte sniff for declared image/PDF types to defeat spoofing).
- New integration events in `TaskManager.Contracts.Events` (records, `DateTimeOffset`,
  denormalized for downstream consumers — no domain logic, no EF):
  - `AttachmentAddedEvent(Guid TaskId, Guid BoardId, Guid AttachmentId, Guid UploadedById, string FileName)`
  - `AttachmentRemovedEvent(Guid TaskId, Guid BoardId, Guid AttachmentId, Guid ActorId, string FileName)`
- Extend the `IBoardBroadcaster` port with `AttachmentAddedAsync` / `AttachmentRemovedAsync`.

### Infrastructure (Tasks)

- `MinioFileStorage : IFileStorage` using `AWSSDK.S3` pointed at the MinIO endpoint.
  Bucket auto-created on startup if absent.
- EF Core configuration + migration for the `attachments` table.
- Integration events are dispatched through the **existing** `TasksDbContext`
  MassTransit EF Core outbox — no new messaging plumbing.

### Presentation (Tasks) — board-membership authorization

| Endpoint | Behavior |
|---|---|
| `POST /api/tasks/{id}/attachments` | `multipart/form-data`, single file → `201` + `AttachmentDto`. No `If-Match` (child collection). Per-route Kestrel body-size limit. |
| `GET /api/tasks/{id}/attachments/{attId}/content` | Streams bytes from MinIO with **`Content-Disposition: attachment; filename="..."`** always — never inline-rendered (blocks stored-XSS via SVG/HTML). |
| `DELETE /api/tasks/{id}/attachments/{attId}` | `204`. Any board member may delete. |

Add/remove paths broadcast live via `IBoardBroadcaster` → `SignalRBoardBroadcaster`
(new `AttachmentAdded` / `AttachmentRemoved` hub messages on the board group).

### Analytics

Consume `AttachmentAddedEvent` (and `AttachmentRemovedEvent`) via the existing
`AnalyticsDbContext` MassTransit EF Core **inbox** (dedup → no double-counting).
Append an activity row ("Alice attached report.pdf") to the per-board activity feed.
The v1.1 activity panel renders it with no frontend change.

### Frontend (Angular)

Attachments section on the task-detail view:
- List: filename, size, uploader, uploaded-at (converted to local at display), download link.
- Upload button (single file; drag-drop optional, not required for v1.2).
- Delete control.
- Live updates via the existing board hub signal, wired to the new `AttachmentAdded` /
  `AttachmentRemoved` hub messages.

## Configuration / Infra

- `docker-compose.yml`: add a `minio` service (API + console), data volume on `D:` to
  match the machine's disk layout, healthcheck.
- New canonical env vars (added verbatim to spec §8 *Secrets*):
  `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`.

## Security notes

- `Content-Disposition: attachment` on every download — no inline rendering.
- Validate content-type **and** extension; magic-byte sniff for declared image/PDF.
- Object keys are server-generated and namespaced by board/task; the client filename is
  never used to construct the storage key.
- Bounded streaming with the per-route request-body-size limit; no full in-memory buffering.

## Testing

- **Domain:** `Attachment` factory / invariants.
- **Application:** upload/delete handler tests with a mocked `IFileStorage`; size and
  type rejection; 20-attachment cap; membership checks.
- **Integration (Testcontainers MinIO):** upload → download round-trip, membership auth,
  oversize rejection, bad-type rejection.
- **Analytics:** `AttachmentAddedEvent` inbox → activity row.
- **E2E (Playwright):** upload a file → a second member sees it appear live → download it
  → activity entry shows.
- **Architecture (NetArchTest):** stays green — `IFileStorage` in Application, MinIO impl
  in Infrastructure; Domain references no external packages.

## Out of scope for v1.2

- Image thumbnails / previews.
- Multiple-file (batch) upload in a single request.
- Presigned-URL direct-to-MinIO uploads (revisit if app bandwidth becomes a concern).
- Virus scanning.
- Versioning / replacing an attachment in place (delete + re-upload instead).
