# v1.3 — OAuth / Social Login — Design

**Date:** 2026-07-07
**Status:** Approved
**Target:** spec addendum §13.6 (flips the §1 "OAuth / social login" non-goal)
**Branch:** `feature/oauth-login` off `develop`

## Summary

Add "Continue with Google" and "Continue with GitHub" to the login and register
screens. Server-side OAuth 2.0 authorization-code flow hosted by the Identity
service; token delivery to the SPA reuses the existing refresh-cookie machinery
unchanged. Auto-link to an existing account when the provider asserts a
**verified** matching email. Sign-in/sign-up only — no connected-accounts
management UI in this release.

## Decisions (made during brainstorm)

| Decision | Choice | Alternatives rejected |
|---|---|---|
| Providers | Google + GitHub | single-provider (same work, less value) |
| Flow | Server-side code flow on Identity | SPA-side PKCE (GitHub token exchange needs a client secret server-side anyway); Keycloak broker (heavy, replaces the hand-rolled JWT/refresh centerpiece) |
| Email collision | Auto-link when provider email is **verified**; reject unverified | explicit-link-only (friction + settings UI); duplicate accounts (confusing) |
| Scope | Sign-in only | management UI (link/unlink/set-password) deferred |
| Dependencies | Zero new NuGet packages | `AspNet.Security.OAuth.GitHub` (Apache-2.0; in-box generic handler suffices) |

## 1. Flow

1. SPA button performs a full-page navigation to
   `GET /api/auth/external/{provider}?returnUrl=/boards` (gateway → Identity).
2. Identity validates `provider ∈ {google, github}` (+ `fake` in Development)
   and that `returnUrl` is a **relative path** (open-redirect guard;
   default `/boards`), then issues `Challenge` for the provider scheme.
3. Provider redirects back to `GET /api/auth/external/callback` on the same
   gateway origin — the correlation/state cookies work because the entire
   dance happens on the origin the browser sees.
4. The callback reads the external principal from the temp cookie scheme,
   dispatches `ExternalLoginCommand`, and on success mints the usual refresh
   token, sets the existing `HttpOnly; Secure; SameSite=Strict;
   Path=/api/auth/refresh` cookie, and 302-redirects to the SPA
   `/auth/callback?returnUrl=...`.
5. The SPA `/auth/callback` route calls the existing `POST /api/auth/refresh`
   to obtain its access token. No new token-delivery mechanism.
6. Failures 302-redirect to `/login?error=<code>` (browser navigation cannot
   receive JSON). Codes: `email-unverified`, `provider-error`.

`localhost:4200 → localhost:5000` is same-site (SameSite ignores ports), so the
Strict refresh cookie behaves exactly as it does for password login. The §10
eTLD+1 deployment caveat is unchanged.

## 2. Sign-in orchestration (Application layer)

`ExternalLoginCommand { Provider, ProviderKey, Email, EmailVerified,
DisplayName }` → `Result<AuthHandlerResult>` — identical to the existing
login/register handlers, reusing `TokenIssuance.IssueAsync` so the callback
endpoint sets the cookie exactly like `AuthEndpoints.AuthResult` does.

Rules, in order:

1. `FindByLoginAsync(provider, providerKey)` hit → sign in that user.
2. Miss, email present **and verified**, `FindByEmailAsync` hit →
   `AddLoginAsync` (auto-link) → sign in.
3. Miss, email present **and verified**, no existing user → create `AppUser`
   (`EmailConfirmed = true`, `UserName` = email, display name from provider
   claim, **no password**) → `AddLoginAsync` → sign in.
4. Email missing or unverified → `Result.Fail("email-unverified")`.

Notes:

- `AspNetUserLogins` already exists in the Identity schema
  (`IdentityDbContext<AppUser, IdentityRole<Guid>, Guid>`) — **no migration**.
- Password login for a passwordless OAuth-only user fails as plain
  "invalid credentials" (`CheckPasswordAsync` on null hash) — correct, no
  special-casing.
- Refresh-token issuance, rotation, reuse detection, and hashing are reused
  untouched.

## 3. Provider registration (Infrastructure/Program)

- **Google:** the in-box generic `AddOAuth` handler (the Google-specific
  package is a separate NuGet dependency; generic OAuth ships in the shared
  framework). Endpoints: `accounts.google.com/o/oauth2/v2/auth`,
  `oauth2.googleapis.com/token`, userinfo
  `openidconnect.googleapis.com/v1/userinfo` (returns `email`,
  `email_verified`, `name`). Scopes `openid email profile`.
- **GitHub:** the same in-box generic `AddOAuth` handler: GitHub
  authorize/token endpoints, scope `user:email`, userinfo from
  `https://api.github.com/user` plus one call to
  `https://api.github.com/user/emails` to obtain the **verified** primary
  email (GitHub's `/user.email` field may be null/unverified).
- **External cookie scheme** `Identity.External` added to stash the provider
  principal between callback legs (`AddIdentityCore` registers none). Short
  lifetime (5 min), deleted after use.
- **Fake provider (Development/CI only):** when `OAUTH_FAKE_ENABLED=true`,
  Identity self-hosts an in-proc stub (`/fake-oauth/authorize`, `/token`,
  `/userinfo`, ~60 lines) registered as provider `fake` via the same generic
  `AddOAuth` handler. The authorize page auto-submits a fixed test identity
  (email configurable via query for E2E variety). Never registered when the
  flag is absent; compose override sets it for the E2E job.
- A provider registers **only if its client id is configured** — missing
  credentials mean the provider silently doesn't exist rather than a startup
  failure.

## 4. Config & discovery

New env vars (spec §8 addendum, same names across environments):

```
OAUTH_GOOGLE_CLIENT_ID / OAUTH_GOOGLE_CLIENT_SECRET
OAUTH_GITHUB_CLIENT_ID / OAUTH_GITHUB_CLIENT_SECRET
OAUTH_FAKE_ENABLED            # never honored outside Development
FRONTEND_URL                  # SPA origin the callback redirects to (default http://localhost:4200)
```

The fake provider additionally reads `FakeOAuth:PublicUrl` (browser-facing
authorize URL base, default the gateway `http://localhost:5000`) and
`FakeOAuth:SelfUrl` (Identity's own address for the server-to-server token /
userinfo legs) from `appsettings.Development.json` / compose env.

`GET /api/auth/external/providers` → `["google","github"]` (enabled subset,
includes `fake` when registered). The SPA renders only the returned buttons;
a fresh clone with no OAuth credentials shows no external buttons and nothing
breaks.

Gateway: the existing `/api/auth/*` route to the identity cluster covers the
new endpoints; verify during implementation, no new route expected.

## 5. Frontend (Angular)

- **Login + register screens:** divider ("or") + branded provider buttons
  (violet theme, provider logos as inline SVG), rendered from the providers
  endpoint via a small `ExternalAuthService`. Click →
  `window.location.assign('<apiUrl>/api/auth/external/<p>?returnUrl=' + ...)`.
- **`/auth/callback` route:** new lightweight component; calls
  `AuthStore.completeExternalLogin()` (wraps the existing refresh call to
  populate the store), then `router.navigateByUrl(returnUrl)`; on failure
  routes to `/login` with the generic error toast.
- **`/login`** reads `?error=` and shows the existing error style with a
  mapped message.
- No settings/management UI.

## 6. Error handling

- Provider denial / handler failure (`RemoteFailure`) → redirect
  `/login?error=provider-error`.
- Unverified/missing email → `/login?error=email-unverified`.
- Malformed or absolute `returnUrl` → replaced with `/boards` (never echoed).
- The callback endpoint is presentation-layer; it maps `Result` failures to
  redirects (not `ToHttpResult`) because the client is a navigating browser.
- Genuine bugs still surface through `ExceptionHandlingMiddleware` as 500s.

## 7. Testing

- **Unit (Identity.Tests):** `ExternalLoginCommandHandler` rules 1–4 of §2;
  returnUrl validation helper (relative ok, absolute/protocol-relative
  rejected).
- **Integration (Mvc.Testing + Testcontainers):** register a test
  authentication scheme standing in for the provider; assert: new user
  created with confirmed email + login row; second sign-in reuses the user;
  verified matching email auto-links to the pre-existing password account;
  unverified email → redirect with `error=email-unverified`; refresh cookie
  present on the callback redirect; absolute returnUrl not followed.
- **E2E (Playwright):** full round trip through the fake provider on the
  compose stack — click "Continue with Fake" (button appears because the
  providers endpoint includes it), stub auto-consents, land on `/boards`
  authenticated; second run signs into the same account.
- **Jest:** providers-endpoint-driven button rendering; callback component
  calls refresh and navigates; error-param mapping on login.

## 8. Out of scope

- Connected-accounts management UI (link/unlink, set password) — possible v1.3.1.
- Additional providers (Microsoft, Apple).
- Mobile app and multi-tenancy remain §1 non-goals.

## 9. Release mechanics

Spec addendum §13.6. One PR `feature/oauth-login` → `develop`, TDD
(test-first a/b halves per task), subagent-driven execution, then a
`release/1.3.0` cut following the established flow.
