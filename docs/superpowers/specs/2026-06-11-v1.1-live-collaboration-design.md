# v1.1 "Live Collaboration" — Design

**Date:** 2026-06-11
**Status:** Approved (brainstorming session)
**Baseline:** v1.0.0 (all 8 playbook steps merged; 20 E2E flows green in CI)
**Relationship to spec:** Extends `smart-task-manager-spec.md`. Each feature lands a
v1.1 addendum in the spec as part of its PR — the spec remains the source of truth.

## Goal

A coherent release themed around collaboration, prioritized portfolio-value-first
(A), usability second (B): open the same board in two browsers and watch them stay
in sync, see who else is viewing, follow a live activity feed, and organize work
with checklists and label filters.

Features in execution order (rationale in *Execution order* below):

| # | Feature | Tier | Surface |
|---|---------|------|---------|
| 1 | Labels & filtering UI | B | frontend only |
| 2 | Subtasks / checklists | B | Tasks domain + frontend |
| 3 | Real-time collaborative boards | A | Tasks SignalR hub + frontend |
| 4 | Per-board activity feed | A | Contracts + Analytics + frontend |

Constraints carried over from v1: free/MIT-only packages, `docker compose up`
starts everything, Onion + Result + DateTimeOffset rules, test-first per phase.
No new infrastructure containers in this release.

## Feature 1 — Labels & filtering UI

The backend is complete and unused: board label CRUD
(`GET/POST /api/boards/{id}/labels`, `DELETE .../labels/{labelId}`), task
attach/detach (`POST/DELETE /api/tasks/{id}/labels/{labelId}`), and
`TaskDto.LabelIds`. This feature is **frontend-only**.

- **Label manager dialog** on board detail: list/create/delete the board's labels.
  Color from a fixed palette of ~12 preset swatches (no free-form color input —
  keeps contrast/accessibility predictable).
- **Label chips on cards**: small colored chips with the label name.
- **Label picker** in the task dialog: toggle attach/detach against the existing
  endpoints.
- **Filter bar** above the columns: free-text (matches title), label multi-select,
  assignee, priority. Composition is AND across filter kinds, OR within the label
  multi-select. Pure client-side filtering in `boards.store.ts` — boards are
  hard-capped at 200 tasks, so in-memory filtering is instant and needs no API
  changes. Active filters serialize to query params (`?label=…&q=…`) so a filtered
  view is shareable/bookmarkable; the board route restores them on load.
- A small "n of m tasks shown" indicator when any filter is active, with a
  one-click clear.

**State:** filters live in the signal store; filtered visible tasks are a computed
signal per column. Drag-and-drop while filtered still moves the real task (position
calculation uses the unfiltered column list).

## Feature 2 — Subtasks / checklists

New child collection on `TaskItem` in the Tasks service.

**Domain:** `ChecklistItem` entity — `Id`, `TaskItemId`, `Title` (1–200 chars),
`IsDone`, `Position`, `CreatedAt`. Private setters + factory + behavior methods
(`Toggle()`, `Rename(...)`), per the domain rules. `TaskItem` gains
`AddChecklistItem`, `RemoveChecklistItem`; items load with the task.

**Endpoints** (Tasks Presentation, same RouteGroup as tasks):

| Verb | Route | Notes |
|---|---|---|
| POST | `/api/tasks/{id}/checklist` | body: `{ title }`; appends at end |
| PUT | `/api/tasks/{id}/checklist/{itemId}` | body: `{ title?, isDone? }` |
| DELETE | `/api/tasks/{id}/checklist/{itemId}` | |

**Concurrency — documented exception:** checklist mutations do **not** require
`If-Match`. They are an independent child collection where last-write-wins is
harmless: two members toggling different items must not 409 each other — that
would punish exactly the collaborative use the feature exists for. Checklist
writes do not touch `TaskItem.RowVersion`. This is recorded in the spec addendum
alongside the `AppUser` setter exception. Item reordering is out of scope
(YAGNI; `Position` = insertion order).

**DTO:** `TaskDto` gains `IReadOnlyList<ChecklistItemDto> Checklist`
(`Id, Title, IsDone, Position`). Cards show a "3/5" progress chip when a checklist
exists; the task dialog gets an inline checklist editor (add, toggle, rename,
delete).

**Events:** none — checklist changes have no analytics meaning (YAGNI). They do
ride the Feature-3 live broadcast like every other task mutation.

**Storage:** new `checklist_items` table in tasks_db via EF migration; cascade
delete with the task.

## Feature 3 — Real-time collaborative boards

The flagship. Card changes made by one member appear instantly for everyone
viewing the board, plus presence ("who's looking at this board now").

**Hub placement — Tasks service, not Notifications.** The hub must verify *board
membership* before a connection may join a board group, and only Tasks knows
membership. Routing broadcasts through RabbitMQ → Notifications would force a
cross-service membership check per connection (latency + coupling) and require fat
events carrying full task snapshots. Hosting in Tasks keeps authorization local
and broadcasts the exact `TaskDto` the service just persisted. Spec §4.4's
"realtime lives in Notifications" statement is amended in the v1.1 addendum:
*user-targeted* notifications stay in Notifications; *board-scoped* sync lives
with the data owner.

**`BoardHub`** (Tasks Presentation, route `/hubs/board`):
- JWT via query string — copy the `OnMessageReceived` wiring from Notifications;
  plain `[Authorize]` on the hub.
- `JoinBoard(boardId)`: validates membership via the board repository; on success
  adds the connection to group `board:{boardId}` and registers presence. Non-members
  get a `HubException`.
- `LeaveBoard(boardId)` and `OnDisconnectedAsync` unwind group + presence.

**Broadcast path:** after each successful mutation (create / update / move /
assign / delete / comment add-edit-delete / label attach-detach / checklist
change), the endpoint broadcasts to the board group:
- `TaskUpserted(TaskDto task, Guid actorId)`
- `TaskDeleted(Guid taskId, Guid actorId)`

This is **best-effort, fire-after-commit**, deliberately *not* through the outbox:
the durable RabbitMQ path (Analytics, Notifications) is untouched; a missed
broadcast self-heals on reload, which is the right consistency class for ephemeral
UI sync. Implementation: a small `IBoardBroadcaster` abstraction in Application,
SignalR implementation in Presentation/Infrastructure boundary so the Onion rule
and architecture tests stay satisfied — handlers return the DTO, endpoints invoke
the broadcaster after a successful `Result`.

**Presence:** `IPresenceTracker` interface with an in-memory, connection-refcounted
implementation (a user with two tabs counts once; last connection leaving removes
them). On change, broadcast `PresenceChanged(IReadOnlyList<Guid> viewerIds)` to the
group. In-memory is correct for the current single-instance deployment; the
interface is the seam for a Redis-backed implementation if Tasks ever scales out
(documented in the spec addendum, not built now).

**SPA:**
- New `core/realtime/board-realtime.service.ts` managing one hub connection with
  `accessTokenFactory`, auto-reconnect, and join/leave on board route enter/exit.
- `boards.store.ts` applies `TaskUpserted` only when the incoming
  `task.rowVersion` is **strictly newer** than the local copy — this drops both
  stale out-of-order frames and the echo of the user's own optimistic mutations.
  `TaskDeleted` removes the card. On SignalR reconnect, refetch the board once
  (events may have been missed while down).
- **Presence avatars** row in the board header (initials chips, "+n" overflow),
  driven by `PresenceChanged`, names resolved via existing user-search caching.

**Gateway:** add `/hubs/board` WS route → tasks-cluster (same pattern as the
existing notifications hub route). CORS already allows the SignalR headers.

## Feature 4 — Per-board activity feed

"Alice moved *Fix login* → Done · 2m ago" — a live, per-board audit trail.

**New contract events** (Tasks starts publishing via the existing outbox):
- `TaskUpdatedEvent` (title/description/priority/dueDate edits)
- `TaskDeletedEvent`

**Event enrichment:** all task events gain `ActorId` and `TaskTitle` fields where
missing, so the feed renders without N+1 lookups into other services. Additive,
but consumers change shape → coordinated in one PR; the RabbitMQ topology
(topic exchange + explicit bindings) is unchanged. Actor *display names* are
resolved client-side through the existing identity user-search cache (ids → names),
keeping Analytics free of Identity coupling.

**Analytics projection:** new `board_activity` table (`Id`, `BoardId`, `TaskId`,
`EventType`, `ActorId`, `TaskTitle`, `OccurredAt`) written by the existing
`EventProjector` (inbox dedup already guarantees exactly-once). Retention: keep the
newest 200 rows per board (trim on insert) — a feed, not an audit log.

**Endpoint:** `GET /api/analytics/boards/{boardId}/activity?count=50` (max 100,
newest first). **Membership enforcement:** Analytics forwards the caller's own
bearer token to Tasks `GET /api/boards/{boardId}`; 200 ⇒ member, anything else ⇒
403. No new service-to-service trust, no shared membership data.

**UI:** collapsible side panel on board detail showing the feed; it refreshes when
a Feature-3 `TaskUpserted`/`TaskDeleted` frame arrives for the board (no polling).
Note the feed write path is eventually consistent (outbox → RabbitMQ → projection),
so the panel may trail the hub frame by a moment — acceptable; the refetch happens
on the signal, and a manual refresh control exists in the panel header.

## Execution order & process

Order **1 → 2 → 3 → 4**: labels first (frontend-only, fastest visible win, zero
schema risk); checklists settle the `TaskDto` shape; live sync then broadcasts an
already-final DTO; the activity feed depends on the new/enriched events and rides
the hub signal for its live refresh.

Per feature, following the project's standing conventions:
- one `feature/<name>` branch → PR into `develop`, Conventional Commits
- test-first (`a` failing tests → `b` green): xUnit for domain/application,
  Jest for SPA, architecture tests must stay green
- each PR extends the Playwright E2E suite; PR #20's required-checks gate (7 checks
  incl. `e2e`) applies automatically
- each PR includes its spec addendum section in `smart-task-manager-spec.md`

**E2E additions:** label filter flow (1); checklist progress flow (2); the
showpiece **two-browser-context sync test** — user A drags a card, assert it moves
on user B's open board without reload, plus presence avatar appears/disappears (3);
activity feed shows a member's action (4).

**Release:** when all four are merged, cut `release/1.1.0` per the runbook
(version bump, CHANGELOG, PR → main, tag `v1.1.0` — tag push triggers
cd-production).

## Risks & judgment calls (decided)

| Decision | Choice | Why |
|---|---|---|
| Hub placement | Tasks service | membership auth is local; fresh DTO; no fat events |
| Broadcast durability | best-effort after commit | ephemeral UI sync; reload self-heals; outbox path untouched |
| Checklist `If-Match` | not required | collaborative toggles must not 409 each other; child collection, LWW harmless |
| Filtering | client-side | 200-task cap makes it instant; zero API surface |
| Presence storage | in-memory behind interface | single-instance today; Redis impl is a drop-in seam |
| Activity membership check | forward caller's bearer to Tasks | no new trust relationships |
| Event enrichment | ActorId + TaskTitle on task events | feed renders without cross-service lookups |
